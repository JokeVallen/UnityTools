## 性能基准测试结果

我们对不同订阅者数量下的发布操作进行了多轮测试，以下为 8 轮测试的平均值汇总（单位：毫秒，数值越小性能越好）。

### 1. 同步发布 (`SyncPublish`)

| 订阅者数量 | 平均耗时 (ms) |
|------------|---------------|
| 0 | 0.000026 |
| 1 | 0.000233 |
| 10 | 0.000594 |
| 50 | 0.002132 |
| 100 | 0.004045 |
| 200 | 0.007991 |
| 500 | 0.019473 |
| 1000 | 0.038654 |

**分析**：同步发布时间随订阅者数量线性增长，单个订阅者调用开销极低（约 0.2 μs），1000 个订阅者也仅需约 0.04 ms，完全满足游戏帧内高频使用。

### 2. 异步串行发布 (`AsyncSerialPublish`)

| 订阅者数量 | 平均耗时 (ms) |
|------------|---------------|
| 0 | 4.15 |
| 1 | 4.14 |
| 10 | 4.14 |
| 50 | 4.09 |
| 100 | 4.05 |
| 200 | 3.99 |
| 500 | 3.80 |
| 1000 | 3.56 |

**分析**：异步串行发布的基础开销主要来自 UniTask 的状态机调度，在订阅者较少时约为 4.1 ms。随着订阅者数量增加，耗时反而略有下降——这是因为在大量订阅者时，UniTask 的内部批处理或线程池调度效率有所提升。实际游戏中异步事件通常用于低频操作（如资源加载），此开销完全可接受。

**带 `Yield` 的异步串行发布**（30 个订阅者均包含 `await UniTask.Yield()`）：  
平均耗时约 **125 ms**，主要因为每个订阅者至少跨越一帧。

### 3. 异步并行发布 (`AsyncParallelPublish`)

| 订阅者数量 | 平均耗时 (ms) |
|------------|---------------|
| 0 | 4.13 |
| 1 | 4.14 |
| 10 | 4.13 |
| 50 | 4.08 |
| 100 | 4.02 |
| 200 | 3.93 |
| 500 | 3.68 |
| 1000 | 3.43 |

**分析**：并行发布在订阅者较少时与串行耗时相近。随着订阅者增多，并行执行的优势显现，1000 个订阅者耗时约 3.4 ms，比串行更快。实际应用中，并行发布适合多个独立的异步任务（如同时请求多个网络接口）。

**带 `Yield` 的异步并行发布**：平均耗时约 **4.11 ms**，因为所有订阅者并发等待，总耗时取决于最慢的那个。

### 4. 订阅与取消订阅开销

| 操作 | 平均耗时 (ms) |
|------|---------------|
| 同步订阅 | 0.0015 |
| 同步取消订阅 | 0.0015 |
| 异步订阅 | 0.0110 |
| 异步取消订阅 | 0.0052 |
| 同步一次性订阅 (`SubscribeOnce`) | 0.0030 |
| 异步一次性订阅 | 0.0195 |
| 带随机优先级的同步订阅（平均） | 0.0378 |

**分析**：同步订阅/取消非常快（约 1.5 μs），异步订阅由于涉及委托包装和 UniTask 结构，稍慢但仍在微秒级。一次性订阅包含额外的状态管理，开销略高，但依然是极轻量级的操作。

### 5. GC 分配测试

| 测试项 | 平均 GC 分配 (字节) |
|--------|---------------------|
| 同步订阅 (含取消) | ~17 B |
| 同步一次性订阅 (含取消) | ~11 B |
| 稳定状态下的同步发布 (100 订阅者) | **0 B** |
| 发布后修改订阅者再发布 | ~17 B |
| 可中断事件发布 (50 订阅者) | 1 B（几乎为零） |
| 清理未使用锁 | ~6 B |
| 异步发布 (CompletedTask) | < 500 B |

**分析**：框架对稳定状态下的同步发布实现了零 GC 分配，非常有利于在 `Update` 等高频循环中使用。异步发布由于 UniTask 内部机制会产生少量分配，但在可接受范围内。

### 6. 高并发吞吐

- **并发发布吞吐量**（50 订阅者，500 次发布）：平均耗时约 **4.2 ms**，即理论上每秒可处理约 **119,000 次发布**。
- **发布过程中并发增删订阅者**：在 300 次发布 + 100 次修改操作下，初始订阅者调用次数符合预期（误差小于 1%），证明快照机制线程安全且可靠。

### 7. 主线程切换开销

- 异步订阅通过 `SubscribeOnMainThread` 包装后，单次发布耗时约 **4.15 ms**，与普通异步发布基本持平，说明 `UniTask.SwitchToMainThread` 的开销在可接受范围内。

## 总结

EventHub 在功能完整性和性能之间取得了优秀的平衡：

- **稳定状态下发布高频同步事件**：零 GC、微秒级延迟，适合 `Update`、物理回调等场景。
- **异步事件**：充分利用 UniTask 的异步能力，支持 `async/await`、取消令牌，同时保持较低开销。
- **Unity 深度集成**：组件生命周期自动管理、主线程调度，极大简化了开发者的心智负担。
- **稳定性**：全面的单元测试和并发测试保证了在各种极端场景下的正确性。
