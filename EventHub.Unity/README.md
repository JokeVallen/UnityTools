## 概述

EventHub 是一个面向 Unity 的通用事件系统，基于 UniTask 构建，旨在为游戏项目提供高易用性、高性能、可扩展的事件解决方案。事件系统将事件的订阅、发布与具体业务逻辑解耦，帮助开发者构建松耦合、易维护的代码架构。

## 核心设计理念

基于"框架 + 默认实现 + 局部与全局 + 覆盖与扩展"的原则进行设计。

- 易用性体现在仅需通过唯一静态类入口或者静态扩展方法来快速上手使用，这使得该事件系统开箱即用，静态类入口提供无线程约束的 API 访问，能够在任何线程进行安全地操作，而针对 Unity 的额外扩展则提供主线程安全调用的途径，开发者只需根据实际需求灵活使用两种方式，而不需要其它任何额外的 API 调用。

- 高性能是该事件系统在维护期间依旧需要不断挑战的目标，事件系统中排序、插入、增删修改、快照机制等可能造成性能瓶颈的部分将成为未来相当一段时间优化的重点。早期版本会优先完善功能和修复功能错误，待功能逐渐稳定和成熟后会逐渐对性能瓶颈部分提供多策略改进，例如根据订阅者数量选择不同的插入算法等，同时也会逐渐提供扩展接口，让开发者能够不再处于"只能使用工具库作者默认实现"的阴影之下，因为作者的实现不一定就是最适合的，所谓人外有人，我们理应让开发者自己也能够去扩展更好或者更适合各自项目的策略。

- 可扩展性采用了"宏覆盖+全局扩展+局部扩展+回退机制"的设计理念，我们将系统各个功能部分进行拆分，并通过宏和接口提供了可覆盖和可替换的方式，例如可以通过实现同步功能的接口来替换事件系统中同步事件的订阅、取消订阅和发布功能，而其它异步和并行等依旧采用默认实现，也可以通过定义指定的宏来覆盖部分或全部默认实现，扩展性将基于事件系统稳定的前提下"从小到大"逐步放宽，所以早期版本可能不会提供太多可扩展的入口，但随着系统设计成熟及功能稳定会逐渐将能够提供扩展性的部分开放。

- 兼容性体现在保证稳定的前提下进行扩展和改进，例如在各个稳定版本发布的框架级接口，后续版本承诺不会进行修改，这是一个通用工具库理应遵守的基本原则，所以即便存在不得已的补充或修改，也应该在继承原有接口功能的基础上进行，所以我们针对接口部分会采用版本接口进行迭代，例如早期版本的同步接口在后续版本中缺少某些方法的定义，我们并不会对原有接口进行改动，而是提供一个2.0版本让开发者可以安全、稳定、自然地过渡到新版本，或者开发者不需要新版本功能也依旧可以继续使用旧版本接口而不用进行任何额外地修改。

## 默认实现的主要功能

### 三种发布模式

默认实现提供了三种基础事件发布模式以适应不同场景：

- **同步发布**：按优先级依次调用所有订阅者的处理函数，适用于需要立即响应且不涉及异步操作的逻辑，例如游戏状态变更、UI 刷新等。

- **异步串行发布**：依次等待每个异步订阅者完成后再继续下一个，适用于需要严格顺序执行的异步任务链，例如资源加载流程。

- **异步并发发布**：同时触发所有异步订阅者，等待全部完成后返回，适用于多个独立异步任务的场景，例如同时请求多个网络接口。对 Unity 单线程而言本身不支持并发，得益于 UniTask 的“分时复用”策略，我们依旧能够在单线程上通过轮转提供“伪并发”的支持，而这依旧在尽可能的最大程度上提供了语义上的并发执行。

### 优先级调度机制

订阅事件时可指定一个整型优先级参数，数值越大执行越靠前，默认实现在内部维护有序的订阅者列表，确保每次串行发布均按优先级降序调用，注意在并发发布中优先级语义失效。

### 线程安全与快照机制

默认实现在内部对订阅者集合的读写操作进行细粒度读写锁保护，发布事件时会生成当前订阅者集合的快照，然后遍历快照执行处理事件，所以从发布开始到完成发布期间的任何订阅与取消订阅都不会同步到此次发布中，可能后续版本会提供发布实时同步的版本，但早期版本不会提供，快照机制允许在事件发布过程中可以安全地接收开发者的订阅和取消订阅操作，这不会在发布过程中引起异常。

### 低内存分配

默认实现在设计上着重优化了高频调用路径的内存分配，在稳定状态下（即订阅者列表不发生变更时），同步发布的整个流程不会产生额外的托管堆分配，适合在 Update 等逐帧调用的场景中使用。早期版本虽然优先于功能完善和功能改进，但对于显然能够提供低内存甚至无内存分配的改进也会采纳。

### 异常隔离与可观测性

默认实现在异常处理方面采用了与 Unity 类似的机制，尽可能避免异常阻断整体系统的运行（除非是不可避免或没有应对机制的异常），单个订阅者的处理函数中抛出的异常不会中断其他订阅者的执行，所有异常可通过全局日志接口记录或通过订阅异常捕获事件进行自定义捕获，便于集中监控和上报。这种"尽可能静默"的机制是早期版本遵从的策略，后续版本可能会提供可选项，开发者可以通过需求自行选择是显式抛出异常还是尽可能静默。

### 丰富的订阅扩展

默认实现内置了几种常用事件的订阅：

- **一次性事件**：处理函数仅执行一次，随后自动取消订阅，避免手动管理生命周期。
- **条件事件**：在事件触发时先通过一个过滤条件判断是否执行处理函数，减少不必要的回调。
- **主线程安全事件**：专门面向 Unity 主线程操作，确保异步处理函数切回主线程后执行，适用于操作 GameObject、UI 等 Unity API 的场合，但注意，如果事件内部自行切换了执行线程，默认实现的主线程安全保障将失效。

### 事件类型的约束

默认实现中针对除特殊事件外的事件类型未提供强制性约束，可以是类和结构体以及其它任何可以作为事件进行调度的类型，但注意早期版本的默认实现的内部采用了统一集合进行存储，所以对于值类型事件会涉及装箱操作，除非在版本日志中明确说明针对值类型事件的优化，否则优先使用类作为事件类型是更明智的选择。

### 特殊事件

默认实现提供了两种可标记事件接口，赋予发布者更精细的控制能力：

- **可中断事件**：在前序订阅者中可设置中断标志，阻止后续订阅者执行，适用于需要短路逻辑的场景（例如技能释放前校验失败即终止）。
- **可取消事件**：允许某个订阅者标记自身为取消状态，发布时该订阅者将被跳过执行，适用于基于条件动态决定是否响应的场景。

### Unity 组件生命周期集成

通过为 UnityEngine.Component 提供的静态扩展方法，开发者可以将订阅与组件的生命周期自动绑定。当组件所挂载的游戏对象被销毁时，其所有关联的订阅均会通过内置的全局监控模块自动取消，彻底杜绝因忘记手动取消导致的悬空引用和内存泄漏。

### 全局配置与扩展点

默认实现提供了运行时替换核心组件的支持，包括：

- 整体或局部事件分发器实现，可灵活替换局部或全局事件系统功能，例如你可能需要在同一个程序的不同需求场景下采用不同的同步事件订阅或发布功能，你可以提前编写一套或多套扩展策略，在运行时动态替换。
- 日志记录器，可将内部日志接入项目已有的日志系统。
- 异常捕获器，可自定义异常处理策略。

### 清理机制

默认实现提供了清理未使用的内部资源的方法，便于在适当时机（如场景加载间隙）主动释放空闲资源来节省内存。

## 适用场景

- 游戏内模块间解耦通信（例如角色死亡通知、分数变化、成就解锁）。
- UI 与数据层的双向绑定。
- 全局系统状态广播（如网络连接状态、玩家登录登出）。
- 异步任务流控制（如资源预加载、顺序动画播放）。
