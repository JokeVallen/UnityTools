## 三、详细对比分析

### 3.1 抽象层开销：直接调用 vs 泛型缓存 vs object 重载

| 调用方式 | 耗时 (ns) | 相对直接调用 |
|----------|-----------|-------------|
| 直接调用 `AppendInt32` | 3.87 | 基准 |
| 泛型缓存 `AppendForNET<int>` | 3.73 | **-3.6%** (无损失) |
| object 重载 (已装箱 int) | 4.39 | +13.4% |

**解读**：
- 泛型缓存通过静态委托实现，JIT 成功内联，性能与直接调用一致。
- object 重载内部有类型 `switch`，略慢且值类型会装箱，应**优先使用泛型版本**。

### 3.2 接口抽象：`IFNVHashable` vs 直接调用

| 调用方式 | 耗时 (ns) |
|----------|-----------|
| 直接调用 (手动组合字段) | 5.79 |
| 接口方法 `AppendHash` | 5.55 |

**解读**：接口调用未产生额外开销（甚至略快，属测量误差），证明 JIT 成功去虚拟化。推荐为自定义类型实现 `IFNVHashable`。

### 3.3 集合处理：库方法 vs 手动循环

| 场景 | 库方法耗时 | 手动循环耗时 | 性能差异 |

**解读**：`AppendArray` 和 `AppendList` 的封装**无性能损失**，代码更简洁且自动处理空检查和长度写入，推荐使用。

### 3.4 缓存冷启动开销

| 状态 | 耗时 | GC 分配 |
|------|------|---------|
| 首次调用某类型组合 | ~0.8 ms | 33 B |

**解读**：冷启动仅发生一次，包含反射创建委托，开销可接受。建议在游戏启动时主动预热常用类型。

## 四、Unsafe 版本专项分析

### 4.1 Guid 哈希性能对比

| 指标 | 安全版本 | Unsafe 版本 |
|------|----------|-------------|
| 单次耗时 | 130.82 ns | **20.58 ns** |
| GC 分配 | 16 B | **0 B** |
| 实现方式 | `ToByteArray()` + 逐字节循环 | 指针直接读取两个 `ulong` |

**性能提升**：耗时减少 **84%**，分配消除，尤其适合频繁处理 Guid 的资源系统、网络同步等场景。

### 4.2 启用方式

1. Unity 中勾选 **Player Settings → Allow 'unsafe' Code**。
2. 在 **Scripting Define Symbols** 中添加 `ENABLE_UNSAFE`。
3. 重新编译即可自动切换。

## 五、使用建议总结

| 场景 | 推荐做法 | 理由 |
|------|----------|------|
| **所有项目** | 使用泛型 API `AppendForNET<T>` / `AppendForUnity<T>` | 零装箱、性能最佳 |
| **自定义类型** | 实现 `IFNVHashable` 接口 | 零成本抽象，代码内聚 |
| **Guid 密集操作** | 启用 `ENABLE_UNSAFE` 宏 | 性能提升 6 倍，消除 GC |
| **集合哈希** | 使用 `AppendForCollection` 或专用方法 | 封装无开销，代码简洁 |
| **首帧性能敏感** | 启动时预热常用类型缓存 | 避免首次调用微小卡顿 |
| **Unity 类型** | 务必使用 `AppendForUnity` 系列 | 误用 `AppendForNET` 将回退至 `GetHashCode`，丧失确定性 |

## 七、常见问题

**Q1：为什么 Unity 类型要用 `AppendForUnity`？**  
A：`AppendForNET` 对未知类型会回退到 `GetHashCode()`，该值在不同平台/进程间不保证一致。`AppendForUnity` 内置了对 `Vector3` 等类型的确定性处理。

**Q2：库支持链式调用吗？**  
A：库本身未提供扩展方法，但开发者可自行添加（见文档示例），不影响性能。

**Q3：是否必须启用 Unsafe？**  
A：非必须，但强烈建议。若发布平台不支持 unsafe（如某些 WebGL 配置），库会自动回退到安全版本，功能不受影响。
